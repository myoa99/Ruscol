## Схема слоев обработки данных (Data Layering)

Архитектура пайплайна разделена на три изолированных слоя:
[ Raw Layer ]  -->  [ Normalized Layer ]  -->  [ Mart Layer ]
(data/raw/)          (data/normalized/)          (data/mart/)

### 1. Слой Raw (`data/raw/`)
* **Формат:** JSON
* **Назначение:** Полная копия ответа API источника (Open-Meteo) без изменений.
* **Гранулярность:** Ответ запроса за период (структура словарных массивов).
* **Зачем нужен:** Обеспечивает воспроизводимость и аудит. При изменении логики очистки не нужно повторно вызывать внешний API.

### 2. Слой Normalized (`data/normalized/`)
* **Формат:** CSV / Parquet
* **Назначение:** Очищенная плоская таблица. Удалены дубликаты, приведение типов (`ts` в datetime, числовые поля в float), добавлена строгая схема.
* **Зерно таблицы:** 1 строка = 1 час наблюдений для `city_id`.
* **Зачем нужен:** Служит единым источником правды для различных задач анализа. Сохраняет детальность сырых данных, но удаляет технический мусор.

### 3. Слой Mart (`data/mart/`)
* **Формат:** CSV
* **Назначение:** Готовая витрина данных для построения дашбордов и отчетов. Данные обогащены человекочитаемыми именами из справочников (`reference/cities.csv`) и агрегированы.
* **Зерно таблицы:** 1 строка = 1 день по конкретному городу.
* **Рассчитанные KPI:**
  * `temp_mean`: Среднесуточная температура (°C).
  * `precip_sum`: Суммарные суточные осадки (мм).
  * `wind_speed_max`: Максимальный порыв ветра за день (км/ч).
  * `rainy_hours`: Количество часов в день с осадками > 0.
  * `temp_mean_rolling_3d`: 3-дневное скользящее среднее температуры.

### Почему нельзя выполнять все в одном файле?
* **Изоляция сбоев:** При изменении схемы источника меняется только код парсинга в Normalized, а логика расчета KPI в Mart остается неизменной.
* **Производительность:** Тяжелые операции очистки выполняются один раз. Витрина строится из уже валидированных таблиц.
* **Переиспользование:** На основе одного Normalized-слоя можно одновременно построить несколько витрин (например, `mart_daily`, `mart_monthly` или `mart_anomalies`).
## Раздел: Инкрементальность и идемпотентность

### 1. Бизнес-ключ (Business Key)
Бизнес-ключ витрины `mart_variant_02` определен как комбинация полей:
`[date, city_id]` (Дата наблюдения + Идентификатор города).
Каждая запись в витрине однозначно идентифицируется этой парой. Дублирование записей с одинаковым бизнес-ключом недопустимо.

### 2. Режимы запуска пайплайна
* **FULL (`--mode full`):**
  * Пересоздает слои `normalized` и `mart` целиком.
  * База данных переписывается через стратегию `if_exists="replace"`.
  * Используется при первичной инициализации или при изменении структуры/логики KPI.
* **INCREMENTAL (`--mode incremental`):**
  * Извлекает и обрабатывает только новые данные, дата которых превышает сохраненный `watermark_date`.
  * При загрузке в БД выполняет атомарный `DELETE` старых записей из диапазона новых данных и `INSERT` (`append`), гарантируя отсутствие дублей при повторных запусках.

### 3. State и Watermark
* **Файл состояния:** `data/state.json`.
* **Watermark:** `watermark_date` (хранит последнюю успешно обработанную дату `YYYY-MM-DD`).
* **Правило обновления Watermark:** Поле `watermark_date` обновляется в `data/state.json` **строго в самом конце** работы пайплайна — только после успешного завершения всех трех шагов (Extract, Transform, Load) и прохождения встроенных SQL-проверок качества данных (Data Quality).
